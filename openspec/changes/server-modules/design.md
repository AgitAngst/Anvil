## Context

Серверы семьи программ ставятся одинаково: бинарник Linux лежит в выпуске GitHub, на машине его запускают как
`<бинарник> install …` под root, он заводит пользователя, службу systemd, порты и сертификат. Центр должен уметь это
для любого такого сервера, а не только для одного.

## Decisions

1. **Где живёт.** Вид «Серверы» в Anvil + крейт `anvil-servers`. Отдельная программа не нужна: Anvil уже центр, у него есть
   задачи, уведомления, палитра, обновления.
2. **Манифест вместо кода.** 80% серверов описываются данными: откуда файл, как назвать службу, какие порты, какие команды.
   Код нужен только для нетиповых страниц, и его добавим, когда понадобится первый такой модуль.
3. **Контракт сервера.** Команды `install`, `status --json`, `backup`, `uninstall`; `install` идемпотентна (повтор = обновление).
   `status --json` печатает объект с полями `name`, `version`, `running`, `address`, `fingerprint` и любыми своими счётчиками —
   центр показывает известные поля и «ещё» для остальных.
4. **Скрытые модули.** Закрытый проект кладёт манифест в папку `modules/` на ПК владельца; в публичном репозитории его нет.
   Поле `hidden = true` прячет модуль из выбора и из списка, пока не включён переключатель.
5. **Безопасность SSH.** Ключ машины запоминается при первом входе (отпечаток показывается владельцу); сменился — отказ с
   отдельным окном. Пароли и ключевые фразы — только в хранилище учётных данных Windows, не в файле настроек. Под не-root —
   `sudo`; без пароля при входе по ключу.
6. **Команды дословно.** Всё, что центр запускает на машине сверх команд контракта (действия, консоль), показывается дословно
   и подтверждается.
7. **Выпуски.** Файл по архитектуре (`x86_64` / `arm64`), сверка по `SHA256SUMS`; нет суммы в выпуске — предупреждение и
   подтверждение владельца. Токен GitHub — в хранилище; для открытых репозиториев не нужен.
8. **Один сервер — несколько экземпляров.** Поле `instances = true`: имя экземпляра добавляется к службе, пользователю,
   каталогу данных и портам (`<служба>-<имя>`). Центр сам подбирает свободные порты и проверяет, что они не заняты.
9. **Пересечение с «Парком серверов».** Парк остаётся как есть (проверка и ваши команды). Слияние видов — отдельное решение
   после того, как «Серверы» поживёт.

## Manifest sketch

```toml
id = "example"
name = "Пример"
hidden = false
instances = false
service = "example"            # имя службы systemd
binary = "/opt/example/example-server"

[source]
repo = "owner/example"          # выпуск GitHub
assets = { x86_64 = "example-server", arm64 = "example-server-arm64" }
checksums = "SHA256SUMS"

[ports]
tcp = [8740]

[commands]                      # {bin} — путь к бинарнику, {args} — поля формы
install = "{bin} install {args}"
status = "{bin} status --json"
backup = "{bin} backup --to {dir}"
uninstall = "{bin} uninstall"

[[form]]                        # поля окна установки
key = "port"
label = "Порт"
kind = "number"
default = 8740
arg = "--port {value}"

[[action]]                      # кнопки «Обслуживания»
label = "Перезапустить"
cmd = "systemctl restart {service}"
confirm = true
```

## Risks

- Живого VPS под рукой нет: SSH-слой проверяется тестовым SSH-сервером в процессе и вручную на машине владельца.
- Манифест, который может запускать команды от root, — это поверхность атаки: манифесты читаются только из папки настроек
  владельца, а команды показываются перед запуском.
- Новые зависимости (`russh`, `keyring`, `reqwest`, `sha2`) — те же, что уже в закрытой админке; согласовать с владельцем до
  кода, версии закрепить.
