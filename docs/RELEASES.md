# Соглашение о выпусках

Как выпускаются программы семьи Anvil. На это опираются `anvil-update` (проверка и установка
обновлений изнутри программы), Anvil (установка и выпуск из окна) и общий workflow выпуска.

## Коротко

| Что | Как |
|---|---|
| Тег | `vX.Y.Z`, пред-выпуск — `vX.Y.Z-beta.N` (`-rc.N`, `-alpha.N`) |
| Версия в `Cargo.toml` | та же `X.Y.Z` — её программа знает о себе (`env!("CARGO_PKG_VERSION")`) |
| Архив под Windows | `<app>-X.Y.Z-windows-x64.zip`: exe и всё, что ему нужно, в корне архива |
| Под Android | `<app>-X.Y.Z-android.apk`, подписанный ключом выпуска программы ([ANDROID.md](ANDROID.md)) |
| Контрольные суммы | `SHA256SUMS` в каждом выпуске: строка `<sha256>  <имя файла>` на файл |
| Заметки | тело GitHub Release — их показывает «Что нового» |
| Где | GitHub Releases репозитория программы или отдельный публичный `<app>-releases` |

## Подробно

**Тег и версия.** Тег ставится на коммит, где версия в `Cargo.toml` уже поднята. Проверка
обновлений сравнивает версии по semver: `0.3.1 > 0.3.0`, `1.0.0 > 1.0.0-rc.1`. Пред-выпуски
предлагаются только тем, кто включил «Предлагать пред-выпуски». Тег без `v` или не из трёх чисел
выпуском не считается.

**Архив.** Имя строго `<app>-<версия>-windows-x64.zip`, `<app>` — то, что программа передаёт в
`anvil_update::Config::new`. Файлы — в корне архива (одна общая папка верхнего уровня тоже
допустима: её снимут при распаковке). В архиве обязательно лежит exe с тем же именем, что у
запущенной программы, — иначе обновление не ставится.

**`SHA256SUMS`.** Без него `anvil-update` обновление не поставит: непроверенный файл хуже старой
версии. Формат как у `sha256sum`:

```
3f5c…9a1e  lantern-desktop-0.3.1-windows-x64.zip
```

**Заметки.** Тело Release, обычный Markdown. «Что нового» показывает заголовки, списки и абзацы.
Общий workflow берёт заметки из аннотации тега, а без неё — список изменений, который собирает
GitHub. Тег с заметками ставить так, иначе git вырежет строки с `#` (заголовки) как комментарии:

```sh
git tag -a v0.3.1 --cleanup=verbatim -F notes.md
```

**Несколько программ в одном репозитории** (Lantern: клиент, сервер, админка) — отдельный архив
на каждую, со своим `<app>`: `lantern-desktop-0.3.1-windows-x64.zip`, `lantern-admin-0.3.1-windows-x64.zip`.
`SHA256SUMS` — общий, по строке на архив.

**Отдельный репозиторий выпусков.** Если Releases репозитория программы нельзя читать без токена, выпуски
публикуются в отдельный публичный репозиторий `<app>-releases` (например, `example/lantern-releases`).
CI репозитория программы публикует туда выпуск токеном с правом записи (секрет `RELEASES_TOKEN`). В репозитории
выпусков должен быть хотя бы один коммит (README). Anvil берёт выпуски программы оттуда же — для установки, «Обновить» и вкладки «Выпуски»:
репозиторий выпусков он читает из `repository:` у вызова общего workflow в `.github/workflows`,
а задать его руками можно в `anvil.toml` у проекта (`releases = "owner/name"` в разделе проекта).
CI по-прежнему смотрится в репозитории кода.

**Подпись.** Общий workflow подписывает exe, если программа передала сертификат подписи кода:
секрет `SIGN_PFX` — файл `.pfx` в base64 (`[Convert]::ToBase64String([IO.File]::ReadAllBytes('cert.pfx'))`),
`SIGN_PASSWORD` — пароль к нему. Подпись — `signtool` с меткой времени, до упаковки, поэтому
`SHA256SUMS` считается уже по подписанным. Нет секрета — exe выходят без подписи, как раньше.
Сертификат виден только шагу подписи, не сборке: build-скрипты зависимостей его не прочтут.
SmartScreen перестаёт предупреждать не сразу: у нового сертификата репутация копится по мере
скачиваний. Обновления изнутри программы (`anvil-update`) предупреждения не вызывают вовсе —
скачанное ими не помечается как «из интернета».

## Под Android

APK выпускается по этому же соглашению: тег `vX.Y.Z`, файл `<app>-X.Y.Z-android.apk` (сборка `github`,
подписанная ключом выпуска программы), строка в общем `SHA256SUMS`, заметки — тело Release. Номер
`versionCode`, подпись, сборки под магазины, workflow и обновление изнутри — в [ANDROID.md](ANDROID.md).
Сборки для RuStore и Google Play в GitHub Release не кладутся: их обновляет магазин.

## Лимит запросов GitHub

Проверка обновления спрашивает у API список выпусков без токена, а анонимных запросов — 60 в час на адрес
(их выбирают сосед по сети, VPN, другие программы). Ответ 403 или 429 больше не тупик:

1. `anvil-update` сам узнаёт последний обычный выпуск без API — `<сайт>/<репозиторий>/releases/latest`
   переадресует на страницу тега, а архив и `SHA256SUMS` лежат по адресам из этого соглашения
   (`…/releases/download/<тег>/<имя>`). Заметок к выпуску при этом нет, а пред-выпуски не видны.
2. Не вышло и это — ошибка «GitHub: HTTP 403 (rate limit), retry in N min» (по заголовкам ответа); окно
   показывает её понятным текстом на своём языке (`anvil_update::errors::describe`, баннер и `about_status`
   делают это сами; программа с собственным видом зовёт `describe` сама).

## Как устроено обновление

1. Программа при запуске и раз в сутки (если это включено) спрашивает список выпусков.
2. Нашёлся выпуск новее — ненавязчивый баннер: «Вышла vX · Обновить · Что нового · Позже ·
   Пропустить эту версию». Модальных окон при запуске нет.
3. «Обновить»: скачать архив → сверить SHA-256 → распаковать рядом → поставить:
   - **портативная копия** (exe где угодно): новые файлы на место старых, старые переименовываются
     в `имя.old-<время>` (запущенный exe Windows переименовать разрешает), уборка — при следующем запуске;
   - **установка Anvil'ом**: `…\<app>\versions\<версия>\` и junction `…\<app>\current` на активную;
     новая версия ставится рядом, `current` переключается, прежние остаются для отката.
4. «Перезапустить» — новая версия запускается с теми же аргументами, старая закрывается.

Что бы ни сломалось по дороге (сеть, сумма, место на диске), рабочей остаётся старая версия.

**На Android** обновляется сборка `github` — модулем `anvil-update` Android-набора (Kotlin; сборки `rustore` и `play`
обновляет магазин). Выпуск тот же: тег `vX.Y.Z`, `<app>-X.Y.Z-android.apk` и `SHA256SUMS`; так же — баннер, проверка
SHA-256, обход лимита через `releases/latest`, пропуск версии и пред-выпуски по флажку. Отличия: проверка — при каждом
запуске программы, а не раз в сутки; выпуск без APK этой программы пропускается (а не показывается ссылкой); вместо
замены файлов и `current` APK ставит установщик системы, и установку подтверждает человек (перед первой установкой —
ещё разрешение «Установка неизвестных приложений»); отката версии нет. Подробно —
[ANDROID.md](ANDROID.md#6-обновление-сборка-github).

## Выпуск из Anvil

Кнопка «Выпуск…» в карточке проекта ведёт мастер по шагам:

1. **Проверки:** рабочая копия чистая, ветка совпадает с origin, `cargo test` и `cargo clippy` зелёные.
2. **Версия:** patch / minor / major от большей из версии в `Cargo.toml` и последнего тега, или своя.
   Правятся версии пакетов, общая версия workspace и `version` у path-зависимостей между своими
   крейтами (форматирование и комментарии `Cargo.toml` сохраняются), затем `cargo update --workspace`.
3. **Заметки:** черновик из коммитов после прошлого тега, правится в окне.
4. **Выпуск** — после подтверждения, где по порядку написано всё, что произойдёт:
   - есть workflow выпуска → коммит `Release vX.Y.Z`, тег (`--cleanup=verbatim`), `git push --atomic`;
     дальше Anvil следит за прогоном по тегу и показывает опубликованный выпуск;
   - workflow нет → Anvil сам собирает release, упаковывает по соглашению, коммитит, ставит тег,
     отправляет и создаёт GitHub Release с архивами и `SHA256SUMS`;
   - origin не на GitHub → архивы по соглашению остаются в `target/anvil-release/vX.Y.Z`.

Сборка идёт **до** коммита и тега: если она сломается, наружу ничего не уйдёт.

## Общий workflow

`.github/workflows/rust-release.yml` в репозитории Anvil — многоразовый: собирает бинарники под
Windows, упаковывает по соглашению, считает `SHA256SUMS` и публикует Release. В программе:

```yaml
# .github/workflows/release.yml
name: Release
on:
  push:
    tags: ["v*"]
permissions:
  contents: write
jobs:
  release:
    uses: AgitAngst/Anvil/.github/workflows/rust-release.yml@kit-v0.2.0
    with:
      app: tetrachrome
      bins: tetrachrome
```

Входы: `app` — начало имени архива; `bins` — бинарники через пробел; `package` — пакет cargo, если
бинарники не в корневом; `repository` — куда публиковать (`owner/name`), пусто — сюда же.
Без `app` каждый бинарник ложится в свой архив `<бинарник>-X.Y.Z-windows-x64.zip`, а `SHA256SUMS` —
один на всех: так клиент и админка Lantern обновляются по отдельности.
Для выпусков в отдельный репозиторий — ещё `secrets: RELEASES_TOKEN: ${{ secrets.RELEASES_TOKEN }}`.

Workflow и крейты набора программа берёт с одного и того же тега набора (`@kit-vX.Y.Z` в workflow,
`tag = "kit-vX.Y.Z"` в `Cargo.toml`) — так сборка выпуска повторяема, а по `Cargo.lock` видно, на какой
версии набора программа. Теги набора ставятся только по команде; нужен набор до тега — можно
временно взять коммит (`rev`).

**Три номера в репозитории Anvil.** Набор для ПК, приложение Anvil и набор для Android выпускаются порознь, и
номера у них свои:

| Что | Где версия | Тег |
|---|---|---|
| Набор для ПК: `anvil-ui`, `anvil-update`, `anvil-wallpaper` и общий workflow | `[workspace.package]` в корневом `Cargo.toml` | `kit-vX.Y.Z` |
| Приложение Anvil | `crates/anvil/Cargo.toml` | `vX.Y.Z` |
| Набор для Android (`android/`, [ANDROID.md](ANDROID.md), раздел 13) | `kitVersion` в `android/gradle.properties` | `android-kit-vX.Y.Z` |

Правка только одной части поднимает только её номер. Теги `kit-v…` и `android-kit-v…` выпуска не запускают
(`release.yml` ждёт `v*`), а «последним тегом» программы Anvil считает тег `vX.Y.Z`. Мастер выпуска меняет
в манифестах `Cargo.toml` всё, что равно старой версии: пока номера набора для ПК и приложения разные, он
трогает только свой; совпадут — поднимет оба, и тогда версию править руками. Набор для Android мастер не
знает: `kitVersion` правится руками, по команде владельца.

## Программы семьи

| Программа | Workflow | Архивы | Куда | Секрет |
|---|---|---|---|---|
| Anvil | `release.yml` | `anvil-…` | `AgitAngst/Anvil` | — |
| Tetrachrome | `release.yml` | `tetrachrome-…` | `AgitAngst/Tetrachrome` | — |
| FFMincer | `release.yml` | `ffmincer-…` | `AgitAngst/FFMincer` | — |

Пример выпуска в отдельный репозиторий: клиент и админка Lantern выпускаются `desktop-release.yml` в публичный
`example/lantern-releases`, сервер — своим workflow в репозиторий программы (оба — по одному тегу).
`RELEASES_TOKEN` — fine-grained токен с правом «Contents: Read and write» только на `example/lantern-releases`;
его заводит владелец и кладёт в секреты репозитория программы.
